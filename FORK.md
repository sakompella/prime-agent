# Fork ledger

This fork (`sakompella/prime-agent`, branch `fork/main`) started at upstream tag `v0.10.0` and was rebased onto upstream `main` at `71beca947` (v0.10.1+5) on 2026-10-22.
Goals: the TUI keeps working, Prime works without T3 Code, T3 integration is native, and approvals are not needed (full access only).

Each line is one change: what it does, why, and when to drop it.

- Kernel harness env: upstream (#3564) exports `RLM_SESSION_DIR` and `RLM_HARNESS_STATE_DIR` from the session artifact dir; `kernel_provisioner` also sets `RLM_GLOBAL_HARNESS_STATE_DIR` from the agent dir, and an ephemeral session gets empty `RLM_SESSION_DIR`/`RLM_HARNESS_STATE_DIR` (like upstream's `RLM_SESSION_ID`), so it never writes into harness dirs inherited from the process env (a `--no-session` run launched from another kernel). Drop when upstream blanks inherited harness dirs and `crates/pa-core/tests/kernel_harness_env.rs` passes without this change.
- Edit diffs: the `python_repl` (formerly `ipython`) tool result carries `details.diffs` (`{path, oldStr, newStr, startLine?}` per edit-skill change, in cell order) from the kernel's diff display events, the v0.9.8 shape T3 Code renders as file changes; v0.10.0 collected them in the kernel manager and dropped them in `convert_execute_result`. Drop when upstream ipython details include `diffs` and `crates/pa-core/tests/kernel_edit_diffs.rs` passes without this change.
- TUI edit receipts: the `python_repl` card no longer reads `details.diffs`, so the edit skill's "Edited <path>" receipt and the output line count stay visible. Upstream's card hid both when diffs were present but has no diff renderer, so forwarding diffs (the line above) blanked successful edits. Drop when the TUI renders `details.diffs`, or when upstream stops hiding the receipt; `edit_receipt_survives_forwarded_diffs` in `crates/pa-tui/src/tool_card/ipython/tests.rs` checks the receipt.
- Oversized edit diffs: when an edit's diff display would exceed the runtime's 16 MiB frame cap, the edit skill resends it with `old_str`/`new_str` clipped to 64 Ki characters plus a `[... diff text truncated: ...]` marker and `truncated: true`, which `details.diffs` carries as `truncated`. Upstream's edit skill swallowed the cap error, so a successful edit left no record. Drop when upstream keeps a record for oversized edits and `crates/pa-core/tests/kernel_edit_diff_too_large.rs` passes without this change.
- RPC mode in a daemon worker: `--mode rpc` creates a client-owned daemon session from the CLI session flags (the ACP create builder, `executionMode: "rpc"`) and serves the rpc JSONL protocol over the daemon link ACP uses (`crates/pa-daemon/src/daemon_link.rs`, transport in `crates/pa-daemon/src/rpc/daemon.rs`), so RLM children, agent messages, heartbeats, self-wakes, and `observe`/`unobserve` of child sessions work for T3 Code (observing the bound session's own id is refused, so `unobserve` never detaches the main stream); a `session_binding` rebind attaches the new id (as the TUI does) for the bound session and observed children, which keep reporting the id the client observed and ignore frames from superseded ids; a refused reattach exits 1 for the bound session and closes an observed child. v0.10.0 ran rpc in-process and answered those surfaces with daemon-mode errors; v0.9.8 rpc was a daemon client. Stdin EOF settles and completes the session (exit 0); SIGTERM/SIGHUP exit 143/129 and a lost session or daemon exits 1 with an `Error:` line, also while the EOF settle runs. The upstream in-process rpc modules in `pa-daemon` stay in place, unwired; `pa-cli` drops their wiring (`rpc_engine_factory` and the `HeadlessEmbedding::Rpc` engine build). Drop when upstream rpc attaches to the daemon and `crates/pa-cli/tests/rpc_daemon_e2e.rs` passes without this change.
- RPC `navigate_tree`: forwards `{targetId, summarize?, customInstructions?, replaceInstructions?, label?}` to the daemon's `navigate_tree` and answers its data (`{cancelled, editorText?, summaryEntry?}`), so T3 Code can roll a thread back in place instead of forking. v0.9.8 rpc had no such command. Drop when upstream rpc routes `navigate_tree`; `rpc_navigate_tree_rolls_the_session_back_in_place` in `crates/pa-cli/tests/rpc_daemon_e2e.rs` checks it.
- RPC `get_fork_messages` scope: the rpc command sends the daemon's `get_user_messages_for_forking` with `scope: "activeBranch"` and answers the active branch's user entries, root to leaf, so after a `navigate_tree` rollback T3 Code's turn baseline no longer counts the abandoned prompt. v0.9.8 listed every user entry in file order; the daemon command without `scope` still does, for the TUI `/fork` list, and an unknown `scope` fails. Drop when upstream rpc answers the active branch; `rpc_get_fork_messages_lists_only_the_active_branch` in `crates/pa-cli/tests/rpc_daemon_e2e.rs` checks it.
- Durable tree moves: a plain `navigate_tree` move (no summary, no label) appends a context-neutral `custom` row (`TREE_NAVIGATION_CUSTOM_TYPE`, `"tree_navigation"`, in `crates/pa-core/src/session/mod.rs`) parented at the new leaf, root-level for a move above the first entry, unless the file's last entry already sits at that position. A reload takes the file's last entry as the leaf, so a rollback now survives a resume or revival, for T3 Code and the TUI `/tree` alike. The reported `leafId` (`get_session_tree`, and the connection state that rpc `clone` reads) is the leaf's nearest ancestor-or-self that is neither such a marker nor a `session_state` row (a reopen appends one), so clients never see either row; the no-op check and the branch-summary walk start from that position, and compaction's already-compacted skip looks through a trailing marker. v0.9.8 and v0.10.0 kept a plain move in memory only and reported the raw leaf; summary and label moves already appended a row. Drop when upstream persists plain tree moves; `rpc_navigate_tree_survives_a_resume` and `rpc_resume_keeps_the_reported_tree_position` in `crates/pa-cli/tests/rpc_daemon_e2e.rs` and `a_plain_tree_move_survives_a_reload` in `crates/pa-daemon/tests/session_tree_e2e.rs` check it.
- Session T3 env: upstream (#3574) forwards each client's env as the create's `launch_env` and merges it over the daemon env when it spawns the session's worker. The fork scopes `T3_*` vars (`launch_env::is_session_scoped` in `crates/pa-types/src/daemon/launch_env.rs`) to the session: `apply_worker_env` removes the `T3_*` vars the supervisor inherited before applying the client's, the ready and promotion clears of `ResidentWorker::launch_env` keep its `T3_*` vars so every respawn keeps the session's T3 connection, and a create that reuses a running session takes the newest client's `T3_*` vars for later respawns. The env stays in memory only (it carries the T3 bearer token). Without this a worker saw the stale T3 token of whichever client started the daemon. Revival from disk, the update-restart roster and supervisor adoption start workers without it. Drop when upstream scopes T3 env per session and `rpc_session_kernel_sees_only_its_clients_t3_env` in `crates/pa-cli/tests/rpc_daemon_e2e.rs` passes without this change.
- RLM child T3 env: upstream (#3574) forwards the parent worker's env to an `rlm.spawn` child, and the fork adds the parent's `T3_*` vars to upstream's minimal `rlm.create_session` env (`create_session_launch_env`), so both kinds of child reach their parent's T3 connection. Drop when upstream's `create_session` children inherit session env and `rpc_spawned_child_kernel_sees_its_parents_t3_env` in `crates/pa-cli/tests/rpc_daemon_e2e.rs` passes without this change.
- Kernel `t3` module: `rlm.t3` lists T3 Code's MCP tools once at import (from `T3_MCP_URL` and `T3_MCP_BEARER_TOKEN`; no env means no request) and exposes each as a typed async method (`t3_thread_send` is `await t3.thread_send(threadId, message)`), with `T3Error` carrying T3's message and code and `T3Unavailable` for a missing env, an unreachable server or a rejected token, so T3 sessions call T3 natively instead of through the generic `mcp.call_tool` path. Upstream has no T3 integration. Drop when upstream ships a native T3 surface; `prime-agent-runtime/test/test_t3.py` checks it.
- T3 kernel binding: when `T3_MCP_URL` and `T3_MCP_BEARER_TOKEN` are both set (`T3Code::from_env` in `crates/pa-core/src/t3_code.rs`), the kernel bootstrap imports `rlm.t3` as `t3` (a failed import binds a stub that raises the import error), the system prompt gets a short `# T3 Code` section pointing at `help(t3)`, and `t3-code` leaves the generic MCP list, so the model has one T3 path; the runtime-ready probe requires `rlm.t3` so an older kernel venv rebuilds, and snapshots skip `t3` like `mcp`. Without T3 env nothing changes. Upstream has no T3 integration. Drop with the `t3` module line above; `crates/pa-core/tests/kernel_t3.rs` and the `t3` unit tests in `runtime_code.rs`, `system_prompt.rs` and `t3_code.rs` check it.
- RPC `--goal`: an rpc or ACP create carries `--goal`/`--goal-token-budget` as `initialGoal: {objective, tokenBudget?}` (the v0.9.8 key; the supervisor keeps it on the durable create until a whole-session move, so a respawn replays it only for the session the create opened), and the worker seeds it on a depth-0 session the way print mode does: the create builds the session, starts the goal on a seedable branch (a resumed branch keeps its persisted goal; RLM children never seed), persists the `thread_goal_state` row and answers with the goal live (a failed persist fails the create and announces nothing). The seed predicate now ignores the daemon's own `session_state` row, which every daemon session file carries before its first build. v0.10.0 seeded only in the in-process print runtime, so rpc and ACP sessions started without the goal; the TUI still ignores `--goal`. Drop when upstream's daemon create seeds `--goal`; `rpc_goal_flag_starts_the_sessions_goal` and `rpc_goal_flag_keeps_a_resumed_sessions_goal` in `crates/pa-cli/tests/rpc_daemon_e2e.rs` and the `a_respawned_*_does_not_replay_the_create_goal` tests in `crates/pa-daemon/tests/goal_recovery_e2e.rs` check it.
- RLM collect wait: `rlm.collect(h, timeout_ms>0)` waits for each target's settle funnel (the verdict the settle watcher reaches, bounded by the shared deadline) instead of one `wait_for_idle`, and a blocking collect on a child whose task prompt is still waiting for the parent's turn to end releases that gate. v0.10.0 returned `running` within milliseconds when collect followed `spawn` in the same turn: the unadmitted child is idle by construction, so the idle wait answered at once; waiting on the settle verdict alone would stall 60 s, because the parent's turn cannot end while collect blocks it. v0.9.8 raced each run's settlement against the deadline and started the child at once. Drop when upstream collect waits on the settle verdict; `rpc_collect_right_after_spawn_waits_for_the_child` in `crates/pa-cli/tests/rpc_daemon_e2e.rs` checks it.
- Fork identity: `prime-agent --capabilities` (exactly that one argument, before any config or daemon work; not in `--help`) prints one JSON line `{"fork":"t3fork","contract":2,"version":"<--version>","rpc":[<every command the rpc route table serves>]}` and exits 0, so T3 Code can tell this fork from stock upstream 0.10, which prints the same `--version` and answers `Error: Unknown option: --capabilities` with exit 1. `--version` stays the bare version because the update swap validates it exactly. Bump `T3_FORK_CONTRACT` (`crates/pa-daemon/src/rpc/daemon.rs`) when the T3-facing rpc commands or frames change; contract 2 marks the `python_repl` tool name (upstream #3400), which contract-1 T3 Code renders as a generic tool. Drop when upstream ships its own capability probe; `capabilities_report_the_fork_and_its_rpc_contract` in `crates/pa-cli/tests/capabilities_e2e.rs` checks it.
- RPC tool frames: the daemon worker frames `tool_execution_update` as `{toolCallId, toolName, args, partialResult}` and `tool_execution_end` as `{toolCallId, toolName, result, isError}`, the 0.9.8 frames, so T3 Code, which keys each tool cell by the `toolName` of every frame, keeps a Python cell's display and edit card past its start. Every frame carries the call's own name: since upstream #3400 the model's tool is `python_repl` and a legacy `ipython` call dispatches to it by alias, and upstream named only the update frame by the resolved tool (`crates/pa-agent/src/agent_loop/tool_call.rs`), which split an alias call's cell. T3 Code must accept both names (contract 2). v0.10.0's worker framed only `toolCallId` and the result on both, while its in-process rpc (`session_events.rs`) named the tool (and dropped `isError`); contract 1 promised these frames. Drop when upstream's worker frames name the tool; `rpc_tool_frames_name_their_tool_on_every_frame` in `crates/pa-cli/tests/rpc_daemon_e2e.rs` checks it.
- RLM heartbeat intervals (upstream bug, worth reporting): `rlm_heartbeat.create` and `.update` pass `interval` through `normalize_heartbeat_schedule`, as `/heartbeat` and 0.9.8 do, so the skill's documented `interval="5m"` (any bare `<n><unit>`) means `every 5m`. v0.10.0 parsed the raw text as a cron schedule and rejected every bare interval (`Unsupported cron schedule...`); only `every 5m` worked. Drop when upstream normalizes the kernel's interval; `rlm_heartbeat_takes_a_bare_interval` and `a_bare_interval_schedules_as_its_every_form` in `crates/pa-core/src/session_engine/host_requests.rs` check it.
- History custom-message timestamps: `get_messages`, `observe` and the attach snapshot rebuild a `custom_message` row's `timestamp` as epoch ms, the shape of its live frame and of 0.9.8's history, and the worker stamps the row with the message's own timestamp (`SessionFile::persist_custom_message`), so the replayed value equals the streamed one. v0.10.0 replayed the row's ISO string (and its write instant, a few ms after the frame's), so T3 Code could not match a replayed agent message to the streamed one and showed a child's task twice; the session file format is unchanged. Drop when upstream replays custom rows with their live timestamp; `rpc_history_replays_a_custom_message_with_its_live_timestamp` in `crates/pa-cli/tests/rpc_daemon_e2e.rs` checks it.
